# File formats and provenance

The codecs in `crates/grim-core` are independent Rust implementations of the file layouts and algorithms below. Third-party application code is not bundled. Generated overrides contain records from the user's own game installation and are not part of a source/binary distribution.

## ARZ v3

All numeric fields are little-endian. The 24-byte header contains `u16 magic=2`, `u16 version=3`, followed by record-table offset, record-table size, record count, string-table offset, and string-table size as `u32`.

The record-table offset is absolute. A record's data offset is relative to byte 24. Each record entry contains name index, length-prefixed Latin-1 class, data offset, compressed and uncompressed sizes, and an eight-byte timestamp. Raw record payloads use LZ4 block compression.

Each field contains a `u16` type, `u16` array length, `u32` key-string index, and four bytes per value. Types 0/1/2/3 represent integer/float/string-index/boolean. The string table contains a count followed by length-prefixed strings. Generated partial archives append 16 zero trailer bytes and must pass read-back comparison. The installed ArchiveTool is used as an independent check during local validation.

The writer preserves numeric types, per-level arrays, field values, record class, and timestamp. Only changed records are emitted. It does not invoke AssetManager, redistribute templates, or replace base archives.

## Character saves

The initial little-endian word XOR `0x55555555` is the seed. A 256-entry cipher table is generated by repeatedly rotating the value right one bit and multiplying by `39916801`, with 32-bit wrapping. Byte and word reads XOR against the current state; state updates XOR table entries indexed by the ciphertext bytes. Reading a word as four independent bytes yields a different plaintext and is not interchangeable.

Block IDs are ordinary encoded words. Lengths XOR the state without advancing it. Block checksums store the state directly without advancing it. Inventory and stash contain nested blocks. Strings and UIDs are encoded at byte width; numeric fields are encoded at word width.

The reader records every primitive at its actual width, verifies all block endpoints/checksums, and requires a byte-for-byte replay before editing. After replacing the four relevant words, it replays the stream, reparses the result, and compares every other primitive with the original. It also supports restoring the original point values to reproduce the original encrypted bytes.

Supported layouts:

| Region                          | Version                               |
| ------------------------------- | ------------------------------------- |
| Header / data                   | 2 / 8                                 |
| Block 1, progression            | 5                                     |
| Block 2, attributes             | 8                                     |
| Blocks 3 and 4, inventory/stash | 11                                    |
| Blocks 5, 6, 7, world UIDs      | 1                                     |
| Block 17, shrine UIDs           | 2                                     |
| Block 8, skills                 | 8; empty item-skill binding list only |
| Block 12, lore                  | 1                                     |
| Block 13, factions              | 5                                     |
| Block 14, UI/hotbar             | 7                                     |
| Block 15, tutorials             | 1                                     |
| Block 16, statistics            | 12                                    |
| Block 10, per-difficulty tokens | 2                                     |

The current item layout has the 1.3-era extra words; older layouts are not inferred. Unknown or partial layouts refuse writing. The point editor adjusts the total devotion value by the same delta as the unspent devotion value, preserving the number already allocated.

## Rule semantics

Rules are based on records inspected in the installed base/GDX1/GDX2/GDX3 databases, not memory addresses. Unsupported selections fail if no matching fields were found.

- XP wraps the entire existing difficulty expression before multiplication.
- Loot multiplies miscellaneous slot probability separately from the weights of its candidate tables. A candidate is identified as leading to high-rarity items by traversing actual loot-table references to item classification fields. Multiplying every candidate weight equally is deliberately skipped.
- Spawn changes use ordinary pool definitions and ordinary monster classifications, exclude known scripted naming groups, and preserve champion fields. This is a conservative eligibility filter, not a claim that every quest script has been audited.
- Cooldown changes apply to selected active-skill base times. Negative transmuter modifiers and reactive/proc definitions are excluded.

[GDLoot's independent analysis](https://github.com/ssauvageau-/GDLoot/blob/master/gd_loottables.py) corroborates the distinction between miscellaneous slot probabilities and per-slot weights.
